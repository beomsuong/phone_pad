# Protocol Boundary QA

두 컴포넌트(Android 클라이언트, Python 서버)가 각각 "정상"으로 보여도 연결 지점(JSON 이벤트 계약)에서 어긋나면 컴파일도 통과하고 개별 테스트도 통과하는데 런타임에서만 실패하는 버그가 된다. 이 스킬은 그 경계면을 놓치지 않고 잡는 방법을 담는다.

## 왜 개별 검증으로는 못 잡나

- Android 쪽 JSON 문자열 템플릿(`"""{"type":"MOVE",...}"""`)은 컴파일러가 타입 체크를 하지 않는 순수 문자열이다 — 오타가 나도 빌드는 통과한다.
- Python 쪽 `event.get("dx", 0)`은 키가 없어도 조용히 기본값을 반환한다 — 필드명이 틀려도 예외 없이 "그냥 동작 안 함" 상태가 된다.
- 즉, 양쪽 다 "에러 없음"이 "정상 동작"을 보장하지 않는다. 반드시 두 코드를 나란히 놓고 비교해야 한다.

## 검증 절차

1. **이벤트 목록 추출**: `TrackpadEvent.kt`의 sealed class 각 항목과, `input_controller.py`의 `handle_event`가 처리하는 `type` 값 목록을 각각 뽑는다.
2. **1:1 매핑 확인**: Android에 정의됐지만 서버가 처리하지 않는 타입(무시됨), 서버는 처리하지만 Android가 절대 보내지 않는 타입(죽은 코드)을 식별한다.
3. **필드 단위 비교**: 각 이벤트 타입에 대해 `TrackpadRepositoryImpl.kt`의 직렬화 문자열과 `handle_event`의 `event.get(...)` 호출을 나란히 읽고, 필드명과 타입(Float→float/int 변환 등)이 일치하는지 확인한다.
4. **채널 확인**: MOVE류가 실제로 UDP 클라이언트를 통해 전송되는지, 나머지가 TCP를 통해 전송되는지 코드에서 직접 확인한다 (AGENTS.md 문서만 믿지 않는다).
5. **문서 대조**: `AGENTS.md` 섹션 4/5의 스펙 표가 실제 코드와 다르면, 어느 쪽이 최신 의도인지 확인 후 문서 갱신을 요청한다 — 문서가 코드와 어긋나면 다음 세션의 에이전트가 잘못된 스펙으로 작업하게 된다.
6. **테스트 존재 확인**: 검증 대상 이벤트에 대해 Android(JUnit/MockK)와 Server(pytest) 양쪽에 테스트가 있는지 확인한다. 없으면 "미검증" 항목으로 리포트에 남긴다.

## 발견 시 보고 형식

```
[불일치] {이벤트 타입}
- 위치: {파일 경로}:{라인}
- 기대: {한쪽 코드가 기대하는 필드/타입}
- 실제: {다른 쪽 코드의 실제 필드/타입}
- 수정 제안: {구체적으로 어느 파일의 어느 라인을 어떻게 바꿔야 하는지}
- 영향받는 에이전트: android-dev / server-dev (또는 양쪽)
```

## 검증 시점

전체 기능이 끝난 뒤 한 번에 몰아서 하지 않는다. android-dev와 server-dev 양쪽이 특정 이벤트 타입의 구현을 완료했다고 알려오는 즉시 그 이벤트만 먼저 검증한다 (incremental QA). 초기 단계의 불일치를 방치하면 이후 이벤트 타입에도 같은 실수가 반복되기 쉽다.
